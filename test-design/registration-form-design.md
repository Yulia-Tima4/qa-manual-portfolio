# Тест-дизайн формы регистрации — Юнилогия

## 1. Общая информация

**Проект:** Lomonosov School 
**Объект тестирования:** форма регистрации пользователя  
**Тип документа:** тест-дизайн  
**Цель:** определить набор тестовых данных и сценариев для проверки обязательности полей, обработки вводимых значений и условий отправки формы.

### 1.1. Описание формы

Форма регистрации содержит семь обязательных полей:

1. Фамилия
2. Имя
3. Телефон
4. Email
5. Ник в Telegram
6. Аккаунт в VK
7. Пароль

Дополнительно предусмотрен чекбокс согласия на обработку персональных данных.

### 1.2. Цель применения техник тест-дизайна

Для формирования набора проверок используются следующие техники:

- **Классы эквивалентности** 
- **Анализ граничных значений** 
- **Таблица принятия решений**
- **Попарное тестирование (Pairwise Testing)** 

## 2. Исходные условия и допущения

Подтверждённые условия:

- Форма содержит семь обязательных полей.
- Для регистрации предусмотрен чекбокс согласия на обработку персональных данных.

Неизвестные условия:

- минимальная и максимальная длина каждого поля;
- допустимые символы для фамилии, имени и пароля;
- правила проверки номера телефона;
- требования к формату email;
- допустимый формат ника в Telegram и аккаунта VK;
- наличие дополнительных проверок пароля;
- точные тексты ошибок и способ их отображения.

Если требования к конкретному полю недоступны, примеры ниже используются для проектирования проверок, а не как подтверждение фактических правил системы. Перед выполнением тестирования необходимо уточнить ожидаемое поведение или зафиксировать его по результатам анализа интерфейса.

## 3. Техника № 1. Классы эквивалентности

### 3.1. Назначение

Классы эквивалентности позволяют сгруппировать тестовые данные по общим признакам и не проверять каждое возможное значение отдельно.

Для каждого поля выделяются типовые группы данных: корректные кандидаты, пустые значения, значения с потенциально некорректным форматом и граничные по длине значения.

**Важно:** принадлежность значения к классу не означает, что система обязательно примет или отклонит его. Ожидаемый результат зависит от правил валидации.

### 3.3. Вывод по классам эквивалентности

Для каждого обязательного поля предусмотрены проверки заполненного и пустого значения. Дополнительно выделены классы данных, позволяющие исследовать формат, состав символов и обработку пробелов.

Для email, телефона, ника в Telegram, аккаунта VK и пароля необходимо сверить ожидаемые результаты с реальными требованиями сервиса. Например, допустимость номера телефона без знака `+` или ссылки на VK в конкретном формате нельзя считать установленным правилом без подтверждения.

## 4. Техника № 2. Анализ граничных значений

### 4.1. Назначение

Анализ граничных значений применяется для проверки данных вблизи минимально и максимально допустимых значений. Ошибки в проверках длины и диапазонов часто возникают непосредственно на границах.

Для корректного применения техники необходимо знать допустимые ограничения поля.

### 4.2. Пример проверки длины пароля

Точные ограничения пароля в рамках данного документа не подтверждены. Поэтому ниже приведён **условный пример**, предполагающий минимальную длину 8 символов и максимальную длину 20 символов. Эти значения используются только для демонстрации техники и не являются утверждением о требованиях Юнилогии.

| Проверка | Длина | Ожидаемый результат при условных ограничениях |
|---|---:|---|
| Ниже минимальной границы | 7 символов | Значение не принимается |
| На минимальной границе | 8 символов | Значение проходит проверку длины |
| Выше минимальной границы | 9 символов | Значение проходит проверку длины |
| Ниже максимальной границы | 19 символов | Значение проходит проверку длины |
| На максимальной границе | 20 символов | Значение проходит проверку длины |
| Выше максимальной границы | 21 символ | Значение не принимается |

При проверке необходимо учитывать и другие требования к паролю, если они установлены: допустимые символы, наличие букв разных регистров, цифр или специальных символов.

### 4.3. Пример проверки длины фамилии

Точные ограничения длины фамилии также не подтверждены. Для демонстрации предположим, что допустимая длина составляет от 1 до 50 символов.

| На минимальной границе | 1 символ | Значение проходит проверку длины |

### 4.4. Применение техники к остальным полям

После уточнения требований анализ граничных значений можно применить к:

- имени;
- номеру телефона — минимальной и максимальной длине номера;
- email — ограничениям длины адреса и его частей;
- нику в Telegram — допустимой длине;
- аккаунту VK — длине идентификатора или ссылки;
- паролю — длине и, если предусмотрено, ограничениям состава символов.

**Вывод:** числовые границы необходимо брать из требований или подтверждённого поведения системы. Если они неизвестны, их следует обозначать как допущения, а не представлять как фактические правила формы.

Для более детальной проверки формы можно рассмотреть следующие ситуации:

- пустая фамилия при заполненных остальных полях;
- пустое имя при заполненных остальных полях;
- пустой телефон при заполненных остальных полях;
- пустой email при заполненных остальных полях;
- пустой ник в Telegram при заполненных остальных полях;
- пустой аккаунт VK при заполненных остальных полях;
- пустой пароль при заполненных остальных полях;

Если одновременно нарушено несколько условий, точный порядок и формат отображения ошибок следует определять по требованиям или фактическому поведению интерфейса.

Таблица охватывает основные сочетания заполненности обязательных полей и состояния чекбокса. Отдельные проверки каждого поля позволяют убедиться, что обязательность применяется ко всем семи полям, а не только к форме в целом.

## 6. Техника № 4. Попарное тестирование (Pairwise Testing)

### 6.1. Назначение

Попарное тестирование применяется для сокращения количества проверяемых комбинаций параметров. Его идея заключается в том, чтобы каждое возможное сочетание значений каждой пары выбранных параметров встретилось хотя бы в одном тесте.

Для демонстрации используется упрощённая модель из трёх бинарных факторов:

- фамилия: заполнена корректно / пустая;
- email: корректного формата / некорректного формата;
- пароль: соответствует условным требованиям / не соответствует условным требованиям.

Эта модель предназначена для иллюстрации техники и не заменяет тестирование всех семи полей формы.

### 6.2. Таблица комбинаций

| № | Фамилия | Email | Пароль |
|---|---|---|---|
| 1 | Заполнена | Корректный формат | Соответствует условным требованиям |
| 2 | Заполнена | Некорректный формат | Не соответствует условным требованиям |
| 3 | Пустая | Корректный формат | Не соответствует условным требованиям |
| 4 | Пустая | Некорректный формат | Соответствует условным требованиям |

### 6.3. Принцип сокращения комбинаций

При трёх факторах с двумя возможными значениями каждый полный перебор содержит:

2 × 2 × 2 = 8 комбинаций.

В приведённом примере используются 4 комбинации. Они обеспечивают попарное покрытие выбранных бинарных факторов: для каждой пары параметров встречаются все четыре сочетания значений.

Таким образом, в этой упрощённой модели количество комбинаций сокращено с 8 до 4, то есть на 50%.

Это сокращение относится только к указанной модели из трёх факторов. Оно не означает, что тестирование всей формы регистрации можно сократить на 50% или что гарантированно будут обнаружены все дефекты.

### 6.4. Ограничения применения

- В модели не представлены все семь полей и чекбокс согласия.
- Не учитываются все возможные форматы и ограничения длины.
- Некорректные значения могут иметь несколько разных классов, а не только один.
- Попарное покрытие не заменяет отдельные проверки обязательности каждого поля и граничных значений.

**Вывод:** попарное тестирование целесообразно использовать для сокращения количества комбинаций при большом числе параметров. Для формы регистрации его следует применять вместе с другими техниками тест-дизайна.

## 7. Общие выводы

Для проектирования проверок формы регистрации Юнилогии выбраны четыре техники тест-дизайна:

1. **Классы эквивалентности** — помогают сгруппировать типовые корректные и потенциально некорректные входные данные для семи обязательных полей.
2. **Анализ граничных значений** — позволяет спроектировать проверки минимальных и максимальных ограничений после уточнения требований.
3. **Таблица принятия решений** — помогает охватить сочетания заполненности обязательных полей и состояния чекбокса согласия.
4. **Попарное тестирование** — демонстрирует способ сокращения числа комбинаций выбранных параметров при сохранении попарного покрытия.

Совместное применение этих техник помогает систематизировать тестовые данные, выявить важные сочетания условий и подготовить основу для чек-листа или набора тест-кейсов.
